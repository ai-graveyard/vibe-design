# Vibe Design「设计配方」产品方案

日期：2026-09-11  
状态：首版工作台已实现，覆盖阶段 A–C 的软件功能；阶段 D 与目标用户试用仍为后续建议。实现及验收记录见 [design-recipe-implementation.md](design-recipe-implementation.md)。本文保留产品方案与范围定义。

## 1. 产品决定

在现有风格库之外，增加一个可离线使用的设计配方工作台。用户从精选方案开始，通过可视化选择调整设计，再带走准确的设计说明、参数和参考页面。

核心路径：选场景 → 选起点 → 调整配方 → 核对预览 → 复制或下载 → 在自己的工具中使用。

运行时不调用模型，不要求 API Key，不设置服务端生成队列。用户的选择、预览、组合、保存和导出都在浏览器完成。用户将资料交给自己的 AI 工具后，是否调用模型及其成本由该工具决定。

首要用户是能判断“喜欢哪一个”，但不熟悉设计术语的独立开发者和 Vibe Coding 用户。设计师可以用它快速表达方向，但首版不围绕专业自由画布工作流展开。

验证假设：用户愿意从一个好起点调整少数要素，并且带走的组合资料比单一风格提示词更容易表达目标。当前尚无用户实验支持这个判断。

## 2. 当前项目能提供什么

| 当前依据 | 可复用价值 | 需要补齐的部分 |
| --- | --- | --- |
| `src/data/styleSpecs.ts` 已区分设计语言、流派、布局、材质、美学、动态表现 | 提供组合的概念基础、风格原则和误用说明 | 现有分类不是互相独立的参数；需人工拆出属性归属与组合边界 |
| 30 个独立 HTML Demo | 提供视觉参考、素材和制作经验 | 页面结构、CSS 变量名和交互不同，不能直接合并成通用配方 |
| `src/data/prompts.ts` 已通过前端字符串生成提示词 | 复用双语输出与保留现有业务的约束 | 当前主要围绕单一风格、修改现有网页；需支持新建与修改两种任务 |
| 设备预览、全屏、源码查看、复制与下载 | 复用工作台交互与固定视口缩放的计算 | 预览组件目前读取固定 Demo 地址，需适配动态配方文档 |
| Zustand 持久化设置 | 复用本地偏好保存方式 | 配方需独立存储、版本管理、导入与导出 |
| Demo 已采用内嵌素材的单文件形式 | 为离线参考页提供经验 | 在已检查的源文件和包配置中未发现完整工作台离线机制，不能把静态网站等同于离线应用 |

现有风格库继续承担“看懂一种风格”的职责。配方工作台承担“为我的任务做出一个具体选择”的职责。

## 3. 首版的范围

首版覆盖两类数字界面：产品展示页、工具后台。二者的信息结构差异明显，可以检验系统是否真正支持组合。

- 每类提供 2 种可切换的布局，共 4 个布局模板。
- 每类提供 4 份人工精选的完整配方，共 8 份起点。
- 提供 6 套语义配色、3 组中英文字体搭配、3 档密度、3 套边角与表面处理、2 档动效。
- 这些是建议的内容上限；每个场景只展示适配的选项，不承诺全部排列组合均经过设计审阅。
- 两类场景均检查桌面、平板、手机和自适应视口。手机是响应式界面预览，不代表已支持原生 App 设计。
- 同时支持“新建界面”和“调整现有界面”的导出说明。
- 首版完成浏览器工作台和可下载的离线工作台，两者使用同一套配方数据与渲染逻辑。

首版暂不覆盖海报、PPT、原生移动端、自由拖拽排版、截图分析、自定义代码运行、云端账号和社区发布。海报与 PPT 后续采用各自的版式规则与输出方式，复用配色、字体等共通部分。

## 4. 用户如何完成一次组合

### 进入

首页增加“拼一份设计配方”入口；风格详情页在存在对应配方时提供“以此为起点”。尚未适配的风格继续提供原有参考包，避免让入口暗示所有 30 种风格都可组合。

用户选择“产品展示页”或“工具后台”，立刻看到同一份示例内容下的 4 个完整起点。以缩略图为主，不要求先填项目介绍，也不让用户面对空白画布。

### 调整

桌面使用两栏：左侧为调整项，右侧大面积显示真实预览。导出置于稳定可见的位置，完整说明按需展开。移动端使用“预览 / 调整”切换，保持配方状态一致。

调整项使用可视化卡片、色板、文字样张和紧凑切换按钮。首屏先突出布局、配色、字体；密度、表面与动效归入“更多调整”。

| 用户能理解的选择 | 实际控制内容 | 示例 |
| --- | --- | --- |
| 布局 | 当前场景内的内容组织、模块比例与响应式重排 | 展示页：左右分栏 / 主视觉居中；后台：侧栏 / 顶部导航 |
| 配色 | 背景、表面、正文、次要文字、操作与状态色 | 暖纸朱红、冷灰蓝、深色中性 |
| 字体 | 标题与正文字体、比例、行高、字重、中文回退 | 现代无衬线、衬线标题、技术感标题 |
| 密度 | 间距、行距、容器留白等一组参数 | 舒展、标准、紧凑；交互目标有独立下限 |
| 边角与表面 | 圆角、边框、阴影等协调后的成套处理 | 平面细线、柔和圆角、硬边块面 |
| 动效 | 已实现的过渡和反馈 | 关闭、轻量；均支持减弱动态效果 |

每次调整马上改变预览。文案固定，便于区分视觉变化；用户可选编辑标题、描述、按钮文字，用来检查真实长度，不自动润色或改写。所有输入仅按文本处理。

提供撤销、重做、恢复起点、另存副本。切换配方起点时，在下一状态显示变化说明，并支持撤销；不静默丢弃用户修改。

### 带走

主操作为“复制设计说明”，次操作为“下载设计包”。导出时选择新建或修改任务；修改模式默认保留业务逻辑、路由、接口和核心文案，新建模式描述目标布局和示例范围。

本地自动保存最近一次配方，支持给配方命名、保存多份、导入导出。删除本地存储后可通过 JSON 恢复。离线文件环境若无法持久化，仍可使用导入导出并明确显示保存状态。

分享链接在后续版本加入，首版通过设计包流转，不依赖短链接服务或云端存储。

## 5. 一个完整例子

用户要做产品展示页，从“纸感阅读”配方开始：

1. 保留衬线标题、纸白底色与细分隔线。
2. 布局由主视觉居中换为左右分栏，突出产品截图。
3. 把强调色从朱红换成深绿，背景与正文角色保持协调。
4. 把密度由舒展换为标准，关闭动效。
5. 查看手机布局和长标题换行，输入自己的产品名。
6. 选择“调整现有界面”，复制说明或下载设计包。

输出说明示意：

> 保留现有项目的业务功能和主要内容。采用纸白背景、深色正文、深绿主操作、衬线标题和细线分区。首屏在桌面以左右分栏组织文字与产品画面，窄屏先文字后画面。使用标准间距，关闭装饰性入场动效。具体数值和布局以随附参考页及参数文件为准。

正式输出要包含实际解析出的数值和断点规则；这里的文字只是内容结构示意。预览使用的示例产品与数据应明确标示，不能成为外部 AI 自动替换用户真实业务文案的依据。

## 6. 组合如何保持协调

配方 = 场景 + 布局 + 视觉起点 + 用户覆盖项 + 适用约束。

视觉起点是一整套初始参数和设计意图。用户调整后，结果可以称为“基于瑞士排版的自定义配方”，不保证仍是某个流派的严格复现。

不能把几段现有风格提示词直接连接。例如一个来源要求硬边阴影，另一个要求柔和投影，拼接会把矛盾交给用户的 AI。应先在本地算出唯一的最终结果，再生成说明。

- 属性分工：布局决定网格与重排，字体方案决定字号体系，密度决定间距，表面方案决定边角与阴影；每个属性必须有明确归属。
- 覆盖次序：场景基础值 → 配方起点 → 用户显式修改。最后进行能力与约束校验。
- 尚未支持的技术组合不可选，并解释缺少哪项实现；切换场景时保留兼容修改，明确列出需替换的项目。
- 确定性可用性问题直接指出，例如某个正文与背景色对比不足；给出预设替代，不用未经解释的总评分。
- 审美取舍只做提示，例如“这个组合会弱化纸感”，允许继续。不能将偏好包装成技术错误。
- 原起点中已被替换的指令从最终说明移除；保留仍适用的构图原则。技术问题未解决时不能标示为已验证配方。

首版以人工维护的选项能力与局部规则实现。主要成本是选项制作和组合审阅，不是字符串拼接。

## 7. 预览与导出使用同一个结果

建议新增一条独立的数据处理路径：

`配方选择 → 本地解析与校验 → 最终设计配置 → 预览 / 说明 / CSS / JSON / HTML`

最终设计配置包含布局结构、明确参数、资源引用、适用规则、示例内容和版本。所有输出读取同一份结果；禁止预览用一套默认值、导出继续引用旧风格参数。

预览由少量手工制作的场景模板渲染，结构切换使用模板变体，视觉调整使用语义变量。复用已有 Demo 的设计经验和合适素材，但新增配方渲染器，不向 30 个原始 Demo 任意注入参数。

工具后台预览应包含导航、指标、搜索筛选、数据列表、表单，以及可切换的空状态、加载和错误状态。采用页面内模拟交互；导出的 HTML 明确说明不连接真实服务。

预览要体现所有开放的选择。尚无对应展示的参数不进入首版，避免出现“选项变了，实际效果没变”。使用本地素材和可再分发字体，长中文、英文和无图片情况都需检查。

下载包建议包含：

| 文件 | 用途 |
| --- | --- |
| `design-brief.md` | 人和 Agent 可读的设计决定、应用范围与检查要求 |
| `recipe.json` | 恢复配方；包含格式版本、素材目录版本、起点、覆盖项和最终参数快照 |
| `tokens.css` | Web 直接使用的语义 CSS 变量 |
| `reference.html` | 与当前预览一致的独立参考页，内嵌所需资源 |
| `README.md` | 如何交给自己的工具使用、示例边界与导入方式 |
| `LICENSES.txt` | 实际随包附带的字体和素材来源与许可 |

导入时检查版本和字段，未知版本不静默丢字段；用户原文件可保留并提示不支持的版本。快照用于识别素材升级造成的变化，不能单凭版本号保证旧渲染器行为完全一致；原始参考 HTML 是长期可查看的视觉依据。

首版的 `recipe.json` 是产品配方格式，不能宣称兼容所有设计工具。将来需要跨工具 Tokens 输出时，可增加遵循 [DTCG 2025.10 Format Module](https://www.designtokens.org/tr/2025.10/format/) 的独立导出器。该社区规范定义参数交换格式，不覆盖整个配方、页面结构或审美规则。

## 8. 零 Token 与断网使用分别交付

零 Token：所有核心路径只进行本地数据运算与渲染；无模型请求和后端依赖。托管版本首次仍需要下载静态文件。

断网使用：提供可下载的单文件离线工作台，包含首版全部配方、模板、脚本、样式和必要字体素材。用户下载后双击打开，在断网状态下继续组合、预览、导入和导出。

离线版本应使用独立构建入口，不能直接把使用绝对资源路径、路由与运行时 fetch 的现有站点打包就声称可双击运行。与在线版本共用业务模块，避免维护两套产品逻辑。

离线构建在制作第一个配方时就验证，不留到最后处理。需在 Chrome 与 Safari 的本地文件环境检查剪贴板、下载、存储与字体；复制不可用时提供可选中文本及 Markdown 下载，保存不可用时提供 JSON 导出。

首版不依赖 Service Worker 缓存。之后若用户需要“安装网站后持续离线使用”，再加入离线缓存与版本更新机制。包大小应随实际字体与素材测量，优先复用资源，不为了凑齐选项无界增加下载体积。

## 9. 开发顺序与每一步的退出条件

以下是工作顺序，不是已承诺工期。工程实现与自动检查可由开发 Agent 承担；配方内容需要人工设计审阅，最终视觉取舍由产品负责人确认。

| 阶段 | 交付物 | 进入下一阶段前需要证明 |
| --- | --- | --- |
| A：验证一条完整路径 | 1 个展示页模板、2 份起点、配色与字体调整、说明和 HTML 导出、离线试验入口 | 同一选择在预览、说明和导出中一致；断网能完成一次组合与导出 |
| B：首版完整功能 | 2 场景、4 布局、8 份精选配方、全部首版调整项、撤销、本地保存与版本化导入导出 | 每项变化可见，规则能解释冲突，刷新和导入可恢复状态 |
| C：首版发布准备 | 双语界面、完整离线包、素材许可、设备与交互检查、使用说明 | 在线和本地文件模式均可完成核心流程，精选配方均经过视觉审阅 |
| D：验证后扩展 | 依据用户行为选择移动应用、海报或 PPT 中的一类；补对应模板和输出规则 | 用户需求指向这个载体，而且现有组合确实比单选风格更好用 |

不要先把 30 种风格全部转换为配方再验证工作台。先验证预览与输出的一致性，再扩内容。

## 10. 如何判断方案成立

产品试用建议邀请 5 位目标用户，以已有风格库为对照完成小任务。下面是提议的继续投入标准，不是已有结果：

- 至少 4 位无需口头指导，能从起点调整两个维度、核对预览并带走资料。
- 用户能解释自己改了什么、为什么，比只报风格名更具体。
- 观察是否经常撤销某类选择、找不到适用起点、无法理解选项；优先修正这些问题，不增加更多选项掩盖问题。
- 用户可自愿在自己的 AI 工具中试用导出资料，比较信息缺失和冲突导致的返工。外部 AI 还原质量必须与本工具的确定性导出质量分开记录。
- 如果大多数人只选完整起点然后导出，应收敛为精选配方库，减少调节负担；如果共同卡在缺少某类布局，优先补布局。

工程验收覆盖：配方解析、属性覆盖、冲突提示、版本导入往返、预览与导出一致、撤销恢复、中英长文本、设备布局、键盘操作、模拟交互、断网与复制降级。精选配方全部截图审阅，支持的选项做交叉与边界组合检查；不宣称穷举了所有排列的美学质量。

验收尺寸沿用项目的 390×844、768×1024、1280×800、1440×900，并补充窄窗口和内容压力情况。检查核心使用流程没有模型或第三方运行时请求。

默认不上传用户内容或行为；早期用观察试用和自愿反馈验证需求。

## 11. 本轮建议

先做阶段 A：展示页的 2 份视觉起点，让布局、配色、字体、离线导出形成一条可用路径。用这个结果判断“组合是否更容易表达设计”，再展开首版内容规模。

长期覆盖更多设计任务时，共用配方的颜色、字体、素材方向和设计意图，各载体维护自己的结构规则与渲染器。增长来自新增经过验证的场景与配方，而不是无约束地增加排列数量。
